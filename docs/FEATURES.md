# Фичи

Фича — самостоятельный модуль продукта («Напоминания», дальше другие). У фичи
один сервис с бизнес-логикой и несколько тонких адаптеров: бот, HTTP API, MCP.
Поведение не расходится между входами, потому что адаптеры вызывают одни и те
же методы сервиса, а права проверяются в сервисе по `PrincipalID`.

## Каталог фич

| Фича | Где | Входы | Статус |
|---|---|---|---|
| Напоминания (`reminders`) | `internal/features/reminders` | бот (`/reminders`, кнопка «✅ Выполнено»), API (`/reminders`), MCP (шесть инструментов), WebApp (экран) | ✅ |
| Бусинки (`craft`) | `internal/features/craft` | API (`/craft`, `/workspaces/{id}/catalog`, `/workspaces/{id}/inventory`), MCP (`/mcp/w/{id}`), WebApp (экраны «Запасы» и «Каталог») | ✅ |
| Пространства (`workspaces`) | `internal/workspace` | API (`/workspaces`), MCP (контекст `/mcp/w/{id}`), WebApp (экран «Участники») | ✅ |
| Доступ по токенам (`tokens`) | `internal/auth` + `web/src/features/tokens` | WebApp и API (`/tokens`); MCP только принимает PAT | ✅ |

«Доступ по токенам» — не отдельная продуктовая фича, а инфраструктура входа:
сервис живёт в `internal/auth`, потому что тем же токеном пользуются HTTP API и
MCP. Новые продуктовые фичи добавляются по рецепту
[`ADDING_A_FEATURE.md`](ADDING_A_FEATURE.md) и попадают в эту таблицу.

## Как устроена фича

```text
internal/features/<feature>/
  service.go      бизнес-логика; каждый метод принимает PrincipalID
  feature.go      Feature: Name, RegisterBot, RegisterMCP, Jobs
  schedule/…      чистые функции фичи (у напоминаний — расчёт расписания)
```

Контракты `Feature` и `Job` объявлены в `internal/feature` и реэкспортированы из
`internal/app` (`app.Feature = feature.Feature`, `app.Job = feature.Job`).
Отдельный пакет нужен, чтобы пакет фичи мог реализовать интерфейс: импорт
`internal/app` из фичи дал бы цикл импортов, ведь `internal/app` сам собирает
фичи.

Сборка (`internal/app`):

1. создаёт сервис фичи (с общим логгером и, где нужно, часами);
2. оборачивает его в `reminders.NewFeature` и кладёт в `app.Registry`;
3. передаёт сервис в `httpapi.Deps` — HTTP-обработчики остаются тонкими
   адаптерами;
4. реестр вызывает `RegisterBot`, `RegisterMCP` и `Jobs` при старте.

Тесты фичи делятся на две группы: чистые функции (`schedule`) проверяются без
базы, сервис и HTTP-слой — интеграционно, на `postgres:17` через testcontainers.

## Напоминания

Первая фича. Повторяет поведение n8n-воркфлоу «Cubly Reminder», но владелец —
SSO-пользователь, а не Telegram-аккаунт, поэтому напоминание переживает
перепривязку мессенджера и доступно из любого входа.

### Модель данных

Две таблицы (подробности — [DATABASE.md](DATABASE.md)):

- `reminders` — правило: текст, часовой пояс, вид расписания, дни, время,
  интервал повтора, включено ли, `next_due_at`;
- `reminder_occurrences` — история срабатываний: когда было должно, когда
  отправлено, сколько повторов, статус.

Инвариант: **у напоминания не больше одного активного срабатывания**. Его
обеспечивает частичный уникальный индекс
`reminder_occurrences_active_uidx`, а не только код сервиса.

### Расписание

Правило хранит:

| Поле | Смысл |
|---|---|
| `schedule_kind` | `weekly` или `monthly` |
| `schedule_days` | для `weekly` — ISO-дни недели 1..7 (Пн=1, Вс=7); для `monthly` — дни месяца 1..31 |
| `time_hhmm` | локальное время `HH:MM`, 24 часа, с ведущим нулём |
| `timezone` | IANA-имя часового пояса (`Europe/Moscow`) |
| `repeat_minutes` | 1..1440, интервал повтора неподтверждённого срабатывания |

`schedule.NextDue(after, kind, days, hhmm, tz)` — чистая функция; она же
используется сервисом при создании, правке и включении напоминания.

Правила расчёта:

- возвращается первый момент расписания, который **строго позже `after + 1
  секунда`** (см. ниже), в UTC;
- `weekly` ищет вперёд до 15 дней, `monthly` — до 36 месяцев; если совпадения
  нет, возвращается ошибка;
- для `monthly` день, которого нет в месяце, означает **последний день месяца**:
  31 в феврале — 28 или 29 (високосный год), 31 в апреле — 30. Поэтому дни 30 и
  31 в феврале дают одно срабатывание, а не два: кандидаты совпадают;
- дни нормализуются (сортируются, дубликаты убираются), поэтому хранение и ответ
  API каноничны;
- время «сегодня, но уже прошло» переносится на следующий подходящий день, а не
  срабатывает немедленно.

Зачем `+1 секунда`: тик планировщика, попавший ровно в секунду срабатывания, не
должен назначить тот же момент ещё раз. Поэтому при `after`, равном моменту
срабатывания (или на 1 секунду позже), возвращается уже следующее срабатывание, а
при `after` за две секунды до него — это же срабатывание.

### Переход на летнее время

Правило детерминировано и не зависит от того, как Go трактует неоднозначное
локальное время:

- **несуществующее время** (весенний перевод часов, «дырка»): срабатывание
  сдвигается вперёд на длину «дырки». Например, 02:30 в ночь, когда
  `Europe/Berlin` переводит часы с 02:00 на 03:00, срабатывает в 03:30 CEST
  (01:30 UTC). Для `America/New_York` 02:30 в ночь перевода — это 03:30 EDT
  (07:30 UTC);
- **неоднозначное время** (осенний перевод, час повторяется): срабатывание
  происходит **один раз**, в первое из двух совпадений. 02:30 в ночь перевода в
  `Europe/Berlin` — это 02:30 CEST (00:30 UTC), а не 02:30 CET;
- в поясах без перевода часов (например, `Asia/Oral`, UTC+5) смещение просто
  постоянно.

### Проверка входных данных

Сервис возвращает `*reminders.ValidationError` с русским текстом; HTTP-слой
отдаёт его как `400 bad_request`, бот покажет тот же текст.

| Правило | Ограничение |
|---|---|
| сообщение | 1..1500 символов (считаются руны, пробелы по краям обрезаются) |
| `repeat_minutes` | 1..1440 |
| дни | хотя бы один; `weekly` — 1..7, `monthly` — 1..31 |
| время | строго `HH:MM`, `09:05` да, `9:05` и `24:00` нет |
| часовой пояс | существующее IANA-имя; `Local` запрещён |
| вид расписания | `weekly` или `monthly` |

### Состояние срабатывания

```text
   (планировщик: next_due_at наступил)
             │
             ▼
   нет ───► active ──── подтверждение (кнопка в чате, API, MCP) ──► completed
             │
             └────── правка или выключение правила ──────► cancelled
```

- `active` — сообщение отправлено, кнопка «✅ Выполнено» ждёт нажатия; пока
  срабатывание активно, напоминание повторяется каждые `repeat_minutes`
  (доставку и повторы делает планировщик);
- `completed` — пользователь подтвердил; `completed_at` заполнен, повторы
  прекращаются;
- `cancelled` — правило изменили или выключили, пока срабатывание было активно:
  старое сообщение больше не соответствует тому, что просил пользователь. При
  удалении напоминания строки срабатываний удаляются каскадом.

`next_due_at` пересчитывается:

- при создании включённого напоминания — ближайшее будущее срабатывание; у
  выключенного `next_due_at = NULL`;
- при правке (PUT) — всегда заново от текущего времени, активное срабатывание
  отменяется;
- при выключении — `NULL`, активное срабатывание отменяется;
- при включении — ближайшее будущее срабатывание;
- после фактического срабатывания его двигает планировщик (M3-3).

### Сервис

`internal/features/reminders.Service` — единственная точка бизнес-логики. Все
методы принимают `PrincipalID` и ограничивают каждый запрос владельцем; чужой и
несуществующий идентификатор неотличимы (`reminders.ErrNotFound`). Сервис
принимает часы через `reminders.WithClock(func() time.Time)`, поэтому тесты и
планировщик работают с управляемым временем.

| Метод | Что делает |
|---|---|
| `Create(ctx, principal, Input)` | проверяет правило, считает `next_due_at`, вставляет строку |
| `List(ctx, principal)` | все напоминания пользователя вместе с активными срабатываниями (два запроса, без N+1) |
| `Get(ctx, principal, id)` | одно напоминание с активным срабатыванием |
| `Update(ctx, principal, id, Input)` | полная замена правила в транзакции: строка + отмена активного срабатывания + новый `next_due_at` |
| `Delete(ctx, principal, id)` | удаляет строку; срабатывания уходят каскадом |
| `Complete(ctx, principal, id)` | подтверждает активное срабатывание; если его нет — `ErrNoActiveOccurrence` |
| `CompleteOccurrence(ctx, principal, reminderID, occurrenceID)` | подтверждает конкретное срабатывание и возвращает типизированный результат: `completed`, `already`, `stale`, `not_owner`, `not_found` |

Ошибки: `*ValidationError` (неверный ввод), `ErrNotFound` (нет такого или
чужой), `ErrNoActiveOccurrence` (нечего подтверждать).

`Complete` — обёртка HTTP-контракта: она находит активное срабатывание и
вызывает `CompleteOccurrence`, поэтому кнопка в чате, HTTP и MCP
подтверждают одним и тем же запросом. Разница только в форме ответа: HTTP
сохраняет `404`/`409`/`200`, бот показывает текст нажатия.

### MCP

`reminders.Feature.RegisterMCP` регистрирует шесть инструментов фичи на
`internal/mcpserver.Server`; седьмой, `whoami`, принадлежит ядру сервера. Все
они — тонкие адаптеры над тем же `reminders.API`: никакого SQL, никаких своих
копий правил.

- Расписание описано в форме, удобной LLM: `weekdays` (`mon`..`sun` или 1..7)
  либо `month_days` (1..31), `time` `HH:MM`, `timezone` (по умолчанию — часовой
  пояс профиля), `repeat_minutes` (по умолчанию 10).
- `reminders_update` — частичное обновление на стороне инструмента: сервис
  по-прежнему делает полную замену правила, адаптер читает текущее состояние и
  подставляет пропущенные поля.
- Области доступа: чтение требует `reminders:read`, изменение —
  `reminders:write`. Проверка выполняется до вызова сервиса, текст ошибки
  `insufficient scope: …` видит модель.
- Ошибки сервиса (`ErrNotFound`, `ErrNoActiveOccurrence`,
  `*ValidationError`) превращаются в результат инструмента с `isError: true` и
  понятным текстом, чтобы модель могла исправить аргументы.
- Подробности, схемы и подключение клиентов — [MCP.md](MCP.md).

### Токены доступа

Персональные токены — не фича-экран, а инфраструктура входа: сервис
`internal/auth` выдаёт `cv_pat_…`, хранит sha256 и области доступа, HTTP API
(тег `tokens`) и WebApp управляют ими, а middleware HTTP API и `/mcp`
принимают их как Bearer. Подробности — [API.md](API.md) и [MCP.md](MCP.md).

## Планировщик

`reminders.Feature.Jobs()` возвращает один job `reminders.scheduler`. Он тикает
каждые `REMINDERS_TICK_INTERVAL` (по умолчанию 15 с) и делает одну порцию работы
за тик: не больше 10 напоминаний, по одному, чтобы всплеск должных напоминаний не
открывал сотни доставок одновременно.

Один тик:

1. **Короткая транзакция аренды.** `ClaimDueReminders` выбирает должные строки
   (`enabled` и (`next_due_at <= now` без активного срабатывания **или**
   активное срабатывание с `next_repeat_at <= now`)) c `FOR UPDATE SKIP LOCKED`,
   ставит `lock_until = now + 55 с` и возвращает строки. Второй экземпляр
   сервиса не ждёт освобождения строки, а берёт следующую: параллельные
   планировщики не дублируют отправку.
2. **Отправка вне транзакции.** Сообщение уходит в мессенджер через интерфейс
   `reminders.Delivery`. Пока идёт сетевой вызов, в базе нет ни одной блокировки.
3. **Вторая транзакция результата.** Запись защищена той же арендой:
   `lock_until` из момента захвата — часть условия `UPDATE`, а для первого
   срабатывания ещё и `updated_at` (чтобы не перезаписать правило, которое
   пользователь изменил, пока сообщение летело). Если аренда истекла (её забрал
   другой экземпляр) или правило изменилось, запись отбрасывается с
   `reminders.ErrLeaseLost`: побеждает новое состояние, а не опоздавший
   рабочий.

Что происходит при срабатывании:

- **Первое срабатывание**: создаётся срабатывание (`scheduled_at` = момент, на
  который оно было должно), `next_due_at` пересчитывается от «сейчас» через
  `schedule.NextDue`, `last_error` очищается, аренда снимается. Догон после
  простоя — ровно один: сколько бы тиков ни пропустило, пользователь получает
  одно сообщение, следующее считается от текущего момента.
- **Повтор** (активное срабатывание и `next_repeat_at <= now`): отправляется
  новое сообщение со счётчиком, `repeat_count` растёт, `next_repeat_at = now +
  repeat_minutes`, в `deliveries` ложатся ссылки на новое сообщение, после чего
  предыдущее сообщение удаляется (best effort: ошибка только логируется).
- **Ошибка отправки**: в `reminders.last_error` пишется причина, аренда
  снимается, ничего больше не меняется — следующий тик повторит ту же отправку.
  Поэтому сбой мессенджера откладывает напоминание, а не теряет его.

Аренда — 55 секунд: она с запасом покрывает один сетевой вызов и заметно
короче минимального интервала повтора (одна минута), поэтому упавший процесс не
задерживает напоминание надолго.

### Доставка

Фича не знает про Telegram и Matrix: `reminders.Delivery` умеет `Send`, `Edit` и
`Delete`. Реализация в `internal/app` ходит через `unibot.Runtime`:
`SendToPrincipal` с предпочтением Telegram → Matrix (первый успешный транспорт
получает сообщение, остальные не дублируют), а `Edit`/`Delete` работают по
`SentMessage`.

Ссылки на доставленное (`platform`, `conversation_id`, `message_id` и
`remote_user_id`) сохраняются в `reminder_occurrences.deliveries`, поэтому повтор
может удалить предыдущее сообщение, а подтверждение — заменить текущее. Без
настроенных транспортов отправка возвращает ошибку и попадает в `last_error`.

### Тексты сообщений

Даты — в часовом поясе напоминания, формат `дд.мм.гггг чч:мм` (секунды только в
строке подтверждения). Текст напоминания всегда проходит через
`unibot.EscapeHTML`, разметка — только `<b>`.

Первое срабатывание:

```text
{текст напоминания}

Первое напоминание: <b>05.01.2026 12:00</b>
```

Повтор добавляет счётчик (нумерация с 1):

```text
{текст напоминания}

Первое напоминание: <b>05.01.2026 12:00</b>
Количество повторов: <b>2</b>
```

Подтверждение (кнопка убирается):

```text
{текст напоминания}

✅ Выполнено: <b>05.01.2026 12:15:07</b>
Первое напоминание: <b>05.01.2026 12:00</b>
Количество повторов: <b>2</b>
```

Строка «Количество повторов» появляется только если повторы были:
`repeat_count` в базе считает все сообщения срабатывания, включая первое, поэтому
в тексте показывается `repeat_count - 1`.

Кнопка «✅ Выполнено» — действие `reminders.done` с payload
`<reminder_id>:<occurrence_id>`, ограниченное `PrincipalID` владельца. Срок
жизни кнопки — `max(3 × repeat_minutes, 48 ч)`: стандартных 24 часов не хватает,
если повтор идёт раз в сутки, а после рестарта процесса кнопка остаётся рабочей,
потому что действия хранятся в PostgreSQL.

### Подтверждение

Кнопка, HTTP `POST /reminders/{id}/complete` и MCP вызывают одну и ту же
атомарную операцию: `UPDATE … WHERE status = 'active' AND id = <occurrence>`,
поэтому из нескольких одновременных подтверждений побеждает ровно одно.
Состояние срабатывания до обновления классифицируется, чтобы ответ был
осмысленным:

| Итог | Ответ в чате (Ack) |
|---|---|
| подтверждено сейчас | «Подтверждено ✅» |
| уже было подтверждено | «Уже подтверждено ✅» |
| отменено правкой или выключением | «Это уже неактуальное напоминание» |
| напоминание другого пользователя | «Это напоминание не для вас» (модальное предупреждение) |
| напоминания или срабатывания больше нет | «Напоминание уже недоступно» |

После успешного подтверждения сервис заменяет доставленные сообщения на текст
подтверждения (см. выше) — в том числе когда подтверждение пришло из WebApp:
чат и API показывают одно состояние. Ошибка редактирования логируется и не
отменяет подтверждение.

### Команда `/reminders`

Краткий список напоминаний пользователя: время, дни, текст (до 60 символов) и
пометка «(выключено)». Показывается не больше 20 строк, остаток считается
строкой «…и ещё N». Если `PUBLIC_BASE_URL` — https, к ответу добавляется
кнопка «Открыть приложение» (мессенджеры принимают `web_app`-кнопки только по
https). Команда попадает в `/help` и в меню команд Telegram автоматически:
роутер перечисляет всё, что зарегистрировали фичи.

### Импорт из n8n

Одноразовая команда `cublyverse import-n8n <file>` переносит напоминания
старого n8n-воркфлоу «Cubly Reminder» (Data Table `telegram_reminders_v2`) в
Cublyverse. Полный чек-лист переключения — [MIGRATION_FROM_N8N.md](MIGRATION_FROM_N8N.md).

```bash
cublyverse import-n8n tg.csv --dry-run
cublyverse import-n8n tg.csv                       # DATABASE_URL из окружения
cublyverse import-n8n --format json tg.json --database-url postgres://…
```

- **Форматы.** CSV (заголовок, RFC 4180-кавычки, многострочные сообщения) и
  JSON (массив строк); `--format auto` (по умолчанию) определяет по первому
  символу файла.
- **Те же правила, что у сервиса.** Каждая строка превращается в `Input` и
  проходит `canonicalize` — единственную копию проверок сообщения, часового
  пояса, времени, дней и интервала повтора. Никаких своих правил у импортёра
  нет.
- **`days`.** `1,2,7` — дни недели (Пн=1), `m:19,31` — дни месяца.
- **Отчёт.** Всего строк, импортировано, уже импортировано, помечено удалёнными,
  невалидные (номер строки и причина), присвоено сразу, ждёт входа.
  `--dry-run` ничего не пишет.
- **Идемпотентность.** `legacy_reminders_import.source_reminder_id` уникален,
  поэтому повторный запуск того же экспорта не дублирует напоминания.
- **Только правило.** Состояние в полёте (`awaiting_confirmation`, id сообщений,
  блокировки, счётчики) не переносится: присвоенное напоминание создаётся через
  сервис и получает `next_due_at` от текущего момента.
- **Присвоение.** Владелец старой строки — Telegram user id. Строки ждут в
  `legacy_reminders_import` и превращаются в напоминания SSO-пользователя в
  момент привязки его Telegram (или сразу при импорте, если он уже привязан).
  Присвоение — одна транзакция с `FOR UPDATE SKIP LOCKED`: две одновременные
  привязки не создают дублей. Сбой присвоения не отменяет привязку: строки
  остаются ждать, повторная привязка или повторный импорт их подхватят.
- **Сообщение в чат.** После присвоения пользователь получает «Импортировано
  напоминаний из старого бота: N» (best effort).

### HTTP

Операции тега `reminders` в `api/openapi.yaml` (обзор — [API.md](API.md)):
`GET /reminders`, `POST /reminders`, `GET /reminders/{id}`,
`PUT /reminders/{id}`, `DELETE /reminders/{id}`,
`POST /reminders/{id}/complete`. `PUT` — полная замена: все поля обязательны,
пропущенное не сохраняется. `complete` отвечает `409 conflict`, если активного
срабатывания нет, и `200` с напоминанием, если подтверждение прошло; сообщение в
чате при этом обновляется.
