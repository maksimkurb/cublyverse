# Переключение с n8n

Cublyverse заменяет n8n-воркфлоу «Cubly Reminder», который хранил напоминания в
Data Table `telegram_reminders_v2` и владельцем считал Telegram user id. Эта
инструкция — порядок переключения без потери напоминаний и без состояния, в
котором два бота мешают друг другу.

Порядок важен: сначала останавливается старый воркфлоу, потом импорт, потом
вход пользователей.

## Что переносится, а что нет

Переносится **только правило**: текст, часовой пояс, вид расписания, дни,
время, интервал повтора и флаг «включено».

Не переносится **состояние в полёте**:

- ожидающие подтверждения (`awaiting_confirmation`, `occurrence_id`,
  `current_message_id`) — если пользователь не нажал «✅ Выполнено» в старом
  боте, это нажатие и старое сообщение остаются в старом чате и в новый сервис
  не попадают;
- счётчики повторов, `next_repeat_at`, `last_completed_at`;
- `next_due_at` из старого экспорта: у каждого импортированного напоминания
  ближайшее срабатывание считается заново от момента импорта (или привязки);
- блокировки (`lock_token`, `lock_until`) и `last_error`.

Строки с `deleted=true` пропускаются. Строки, которые не проходят правила
сервиса (время не `HH:MM`, неизвестный часовой пояс, дни вне диапазона и
т. п.), не импортируются: команда печатает номер строки и причину, а остальные
строки импортируются нормально.

## 1. Подготовить новый сервис

Новый сервис должен быть уже развёрнут и проверен — до выключения старого
бота. Минимум:

- `docker compose -f deploy/docker-compose.yml ps` — оба сервиса `healthy`;
- `curl -fsS http://127.0.0.1:8080/readyz` — 200;
- вход в WebApp и одно тестовое напоминание работают (см. чек-лист в
  [DEPLOY.md](DEPLOY.md)).

Если старый и новый бот используют **один токен**, до выключения n8n новый
сервис должен работать без Telegram-транспорта (это нормально: без
`TELEGRAM_BOT_TOKEN` поднимается API и WebApp, бот не запускается). Токен
добавьте в `.env` на шаге 5 — после остановки n8n.

## 2. Выключить n8n-воркфлоу

**Сначала выключите воркфлоу «Cubly Reminder» в n8n** (Deactivate), и только
потом запускайте новый бот с тем же `TELEGRAM_BOT_TOKEN`.

Почему именно так:

- у Telegram один получатель обновлений на токен: второй `getUpdates` получает
  `409 Conflict: terminated by other getUpdates request`, и сообщения достаются
  то одному, то другому боту случайным образом;
- два бота одновременно отвечают на одну и ту же кнопку «✅ Выполнено»:
  напоминание подтверждается в одном месте и остаётся висеть в другом;
- импорт должен видеть последнее состояние таблицы: если воркфлоу продолжает
  писать, часть изменений после экспорта потеряется.

Альтернатива — **новый токен бота** (`@BotFather` → `/newbot` или `/revoke`):
тогда старый и новый бот могут работать одновременно, потому что у них разные
токены и разные очереди обновлений. Минусы: пользователи должны открыть
**нового** бота и пройти привязку заново (старый чат с напоминаниями остаётся в
старом боте), а Telegram user id у человека не меняется, поэтому импорт по
`user_id` продолжает работать. Этот вариант удобен, если нужен плавный переход,
но при одном токене выключение n8n обязательно.

Выключение воркфлоу не удаляет данные: Data Table остаётся, экспорт можно
сделать в любой момент.

## 3. Экспортировать Data Table

В n8n откройте Data Table `telegram_reminders_v2` и скачайте её:

- **CSV** — кнопка экспорта таблицы (файл с заголовком и RFC 4180-кавычками);
- **JSON** — через API/узел n8n: массив объектов-строк.

Поддерживаются оба формата; `--format auto` (по умолчанию) определяет формат по
первому символу. Обязательные колонки: `reminder_id`, `user_id`, `message`,
`timezone`, `days`, `time_hhmm`. Необязательные: `repeat_minutes` (по
умолчанию 10), `enabled` (по умолчанию `true`), `deleted` (по умолчанию
`false`). Остальные колонки игнорируются — включая состояние в полёте.

`days` — либо ISO-дни недели через запятую (`1,2,3,4,5,6,7`, Пн=1), либо дни
месяца с префиксом `m:` (`m:19,31`; день, которого нет в месяце, означает
последний день).

## 4. Пробный прогон

Скопируйте файл в контейнер и запустите импорт с `--dry-run`: он ничего не
пишет, только проверяет строки и показывает отчёт.

```bash
docker compose -f deploy/docker-compose.yml cp telegram_reminders_v2.csv app:/tmp/legacy.csv
docker compose -f deploy/docker-compose.yml exec app \
  cublyverse import-n8n /tmp/legacy.csv --dry-run
```

Пример отчёта:

```text
file: /tmp/legacy.csv (csv)
rows: 42
imported: 0
already imported: 0
deleted in the old bot: 3
invalid: 1
  row 17: Неизвестный часовой пояс
attached to already bound users: 0
waiting for a sign-in: 0
dry run: nothing was written
```

`row 17` — номер записи в файле: заголовок CSV — запись 1, первая строка данных
— 2; для JSON — индекс элемента в массиве (с 1). Разберите невалидные строки:
обычно это опечатка в часовом поясе или время без ведущего нуля (`9:05` вместо
`09:05`). Исправьте их в исходной таблице и экспортируйте заново либо
импортируйте как есть — такие напоминания просто не появятся.

## 5. Импорт

```bash
docker compose -f deploy/docker-compose.yml exec app \
  cublyverse import-n8n /tmp/legacy.csv
```

Что происходит:

- валидные строки попадают в таблицу ожидания `legacy_reminders_import` с
  привязкой к Telegram user id;
- если Telegram-аккаунт пользователя **уже привязан** к SSO (он входил в новый
  сервис), напоминания создаются сразу, и в отчёте это строка
  `attached to already bound users`;
- остальные ждут входа: строка `waiting for a sign-in`.

Импорт идемпотентен: повторный запуск того же файла ничего не дублирует (уникальный
`reminder_id` исходной строки), поэтому его можно безопасно перезапускать — это
же лечит ситуацию «строки импортировались, а привязка тогда не удалась».

Если база развёрнута не в compose, а команда запускается на хосте, передайте
адрес явно: `cublyverse import-n8n --database-url "$DATABASE_URL" <file>`.
`DATABASE_URL` из окружения используется по умолчанию.

## 6. Запустить бота и попросить пользователей войти

1. Впишите `TELEGRAM_BOT_TOKEN` (если ещё не вписан) и примените:
   `docker compose -f deploy/docker-compose.yml up -d`.
2. Попросите каждого пользователя открыть бота, отправить `/start` и пройти
   вход по кнопке «Войти» (SSO + подтверждение привязки). Только в этот момент
   его ожидающие строки превращаются в напоминания: без привязки сервис не
   знает, какому SSO-аккаунту они принадлежат.
3. После привязки пользователь получает в чат «✅ Аккаунт привязан» и
   «Импортировано напоминаний из старого бота: N». Если он уже был привязан,
   сообщение об импорте не приходит — напоминания уже в WebApp.

Проверить прогресс можно повторным импортом в режиме `--dry-run`: строка
`waiting for a sign-in` показывает, сколько строк ещё не привязано.

## 7. Проверить одно напоминание от начала до конца

1. Пусть пользователь создаст (или включит) напоминание на ближайшие 2–3 минуты
   в WebApp.
2. Дождитесь сообщения в чате: текст, «Первое напоминание: …», кнопка
   «✅ Выполнено».
3. Нажмите кнопку: сообщение меняется на «✅ Выполнено: <время>», кнопка
   исчезает.
4. В WebApp напоминание показывает состояние без активного подтверждения.

Если сообщение не пришло — `REMINDERS_TICK_INTERVAL`, строки с
`last_error` в `reminders` и предупреждение `reminders scheduler has no
messenger delivery` в логах (см. [DEPLOY.md](DEPLOY.md), «Диагностика»).

## 8. Откат

Пока n8n-воркфлоу выключен, но не удалён, откат — это вернуть его в строй:

1. Уберите `TELEGRAM_BOT_TOKEN` из `.env` нового сервиса и перезапустите его
   (`docker compose up -d`), чтобы освободить токен.
2. Включите воркфлоу «Cubly Reminder» в n8n (Activate). Старая Data Table не
   менялась импортом — там всё, что было.
3. Напоминания, созданные в новом сервисе за время переключения, в n8n не
   появятся: переносите их вручную или считайте потерянными.

База нового сервиса при этом не удаляется: можно починить проблему, снова
выключить n8n и повторить переключение. Импорт повторно безопасен.

## 9. Уборка

- Сохраните экспорт (`telegram_reminders_v2.csv`) в архив: это снимок старой
  таблицы на момент переключения.
- Через несколько дней, когда все пользователи вошли и напоминания проверены,
  удалите или архивируйте воркфлоу «Cubly Reminder» в n8n, чтобы его случайно
  не включили снова.
- Отзовите старые креденшелы n8n, если они больше не нужны; токен бота теперь
  живёт только в `.env` нового сервиса.
- Проверьте, что в `legacy_reminders_import` не осталось строк, которые уже
  никогда не привяжутся (`claimed_by IS NULL` и пользователь отказался от
  бота). Такие строки можно оставить как историю — они ничего не делают.
