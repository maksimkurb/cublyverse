# Импорт из Grist в каталог «Бусинки»

Одноразовый скрипт, который переносит документ Grist в PostgreSQL Cublyverse:
производителей, каталог материалов, остатки, проекты и связи «проект —
материал». Скрипт не входит в приложение: он лежит вне Go-модуля, не
добавляет зависимостей в `go.mod` и запускается вручную.

Схема-приёмник — `internal/store/migrations/00011_craft.sql` (категории и
единицы измерения берутся оттуда).

## Что нужно

- Python 3.10+;
- доступ к серверу Grist и API-ключ с правом чтения документа;
- PostgreSQL Cublyverse с применёнными миграциями (`make migrate`) и
  существующим рабочим пространством.

```bash
cd scripts/migrate-grist
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
# для тестов дополнительно:
.venv/bin/pip install pytest
```

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `GRIST_URL` | Базовый адрес сервера Grist, например `https://grist.example.com` |
| `GRIST_API_KEY` | API-ключ Grist. Скрипт никогда не печатает и не сохраняет его |
| `DATABASE_URL` | DSN PostgreSQL (можно заменить флагом `--dsn`) |

Ключ передаётся только в заголовке `Authorization` HTTP-запроса. В дамп
`--save-json` он не попадает.

## Запуск

По умолчанию включён **сухой прогон**: скрипт делает всю работу в одной
транзакции, печатает отчёт и откатывает изменения. Чтобы записать данные,
нужен `--apply`.

```bash
# посмотреть отчёт, ничего не менять (по умолчанию)
GRIST_URL=https://grist.example.com GRIST_API_KEY=... \
DATABASE_URL=postgres://... \
python3 migrate.py --workspace <uuid> --user <uuid>

# записать в базу
GRIST_URL=https://grist.example.com GRIST_API_KEY=... \
DATABASE_URL=postgres://... \
python3 migrate.py --workspace <uuid> --user <uuid> --apply
```

- `--workspace <uuid>` — рабочее пространство, куда импортируются позиции.
  Если его нет, скрипт завершается с понятной ошибкой.
- `--user <uuid>` — пользователь, который попадёт в `craft_inventory_log`
  как автор начальных остатков.
- `--dsn` — DSN PostgreSQL, если удобнее передать его флагом.
- `--dry-run` — явно потребовать сухой прогон (он и так по умолчанию).
- `--from-json <файл>` — читать ранее сохранённый дамп вместо Grist
  (Grist и `GRIST_*` при этом не нужны).
- `--save-json <файл>` — сохранить полученные из Grist таблицы, чтобы потом
  повторять импорт через `--from-json`.
- `--doc` и `--grist-url` — переопределить id документа и адрес сервера
  (по умолчанию документ `q8Q3PUwU5uHSnTD6bQo6xC`).

Типичный сценарий: один раз сохранить дамп, затем отлаживать импорт на нём.

```bash
GRIST_URL=... GRIST_API_KEY=... python3 migrate.py \
  --workspace <uuid> --user <uuid> --save-json /tmp/grist.json
python3 migrate.py --workspace <uuid> --user <uuid> \
  --dsn postgres://... --from-json /tmp/grist.json --apply
```

## Что и куда переносится

Читаются четыре таблицы: `MaterialTypes`, `Manufacturers`, `Projects`,
`Materials` (по одному запросу `GET /api/docs/{doc}/tables/{Table}/records`
на таблицу, только стандартная библиотека `urllib`).

1. **Производители** — upsert в `craft_manufacturers` по имени. Пустые
   `Website`/`Notes` из Grist не затирают уже сохранённые значения.
2. **Материалы** — позиции `craft_catalog_items`:
   - если есть и производитель, и артикул, сначала ищется **глобальная**
     позиция (`workspace_id IS NULL`) с тем же производителем
     (без учёта регистра), категорией и артикулом. Найденная — используется,
     новая не создаётся; расхождения старых значений (`name`, `color_name`,
     `color_hex`, `size`, `finish`, а также единица измерения) попадают
     в отчёт как конфликты. Глобальная строка никогда не перезаписывается;
   - иначе создаётся **приватная** позиция с `workspace_id` из `--workspace`:
     категория, производитель, артикул, серия, название, цвет, размер,
     отделка, единица, `source = 'grist-import'`, `source_url` из
     `ManufacturerURL`;
   - `color_hex` переносится, только если значение совпадает с `#RRGGBB`
     (иначе пустая строка и предупреждение), валидный цвет переводится
     в верхний регистр;
   - `color_source` — `approx`, если цвет есть (проверить «официальность»
     нельзя), иначе пусто. Исходный текст `ColorDataSource` сохраняется
     в `attrs.legacy_color_data_source`;
   - в `attrs` также попадают `grist_id` (id строки Grist), `source_text`,
     `notes` и компоненты цвета `color_r`/`color_g`/`color_b`, если они есть;
   - `unit` — из Grist, если это одна из допустимых единиц (`шт`, `г`,
     `моток`, `м`, `см`, `упаковка`, `набор`); иначе единица по умолчанию
     для категории и предупреждение;
   - `UsedIn` (RefList) даёт связи с проектами.
3. **Остатки** — `craft_inventory` (по одной строке на позицию, в том числе
   с нулём) и запись в `craft_inventory_log` (`delta = qty_after = CurrentStock`,
   причина `импорт из Grist`), только когда остаток больше нуля.
4. **Проекты** — `craft_projects` и связи `craft_project_materials`
   (`qty_planned` пустой, `qty_used = 0`).

### Соответствие категорий

| MaterialTypes.Name | slug |
| --- | --- |
| Мулине | `floss` |
| Бисер | `seed-beads` |
| Стеклярус | `bugles` |
| Рубка | `cut-beads` |
| Жемчуг | `pearls` |
| Бусины | `beads` |
| Пайетки | `sequins` |
| Канитель | `bullion-wire` |
| Стразы | `rhinestones` |
| Оправа | `settings` |
| Стразовая цепь | `rhinestone-chain` |
| Шнур / трос | `cord` |
| Ткань | `fabric` |

Материал с неизвестным типом не создаётся — он попадает в отчёт в раздел
«Позиции с неизвестной категорией (пропущены)».

## Правила и краевые случаи

- **Ссылки Grist.** `Ref` приходит числовым id; `0`, `null` и пустое
  значение означают «нет ссылки». `RefList` приходит как `["L", id, ...]`
  или `null`/`[]`; порядок сохраняется, повторы убираются.
- **Дубли в Grist.** Если у двух строк совпали категория, производитель и
  непустой артикул (именно так их видит уникальный индекс
  `craft_catalog_items_article_uidx`), они объединяются: остатки
  суммируются, связи с проектами объединяются, пустые поля заполняются
  из дубля. Объединение перечисляется в отчёте.
- **Отрицательный или нечисловой остаток** превращается в 0 с
  предупреждением: `craft_inventory.qty` не может быть отрицательным.
- **Повторный запуск.** Импорт идемпотентен:
  - приватные позиции ищутся по `attrs->>'grist_id'` (и по списку
    `attrs->'grist_ids'` у объединённых дублей) внутри пространства;
  - проекты — по `(workspace_id, name)`;
  - остаток и запись в журнал создаются только один раз: если строка
    `craft_inventory` уже есть, она не увеличивается;
  - связи «проект — материал» вставляются через `ON CONFLICT DO NOTHING`.

  Поэтому `--apply` можно запускать несколько раз: второй запуск ничего
  не дублирует и показывает нули в счётчиках создания.
- **Существующая приватная позиция с тем же производителем и артикулом**
  (созданная вручную до импорта) переиспользуется, а не дублируется;
  это отмечается в разделе предупреждений.
- Всё выполняется **в одной транзакции**: ошибка или сухой прогон
  откатывают изменения целиком.

## Отчёт

Скрипт печатает по-русски:

- счётчики: производители, созданные приватные позиции, привязки
  к глобальному каталогу, переиспользованные позиции, объединённые дубли,
  строки остатков, записи журнала, проекты и связи;
- конфликты с глобальным каталогом (старое значение и официальное);
- объединённые дубли;
- позиции с неизвестной категорией, нераспознанной единицей и
  некорректным `ColorHex`;
- прочие предупреждения (отрицательный остаток, неизвестный проект и т. п.);
- последняя строка явно говорит, был это сухой прогон или запись.

## Тесты

Юнит-тесты не требуют ни сети, ни базы: они проверяют чистые функции
(маппинг категорий и единиц, разбор ссылок, hex, объединение дублей,
конфликты) на фикстуре `tests/fixture.json`.

```bash
cd scripts/migrate-grist
.venv/bin/python -m pytest -m "not integration"
```

Есть один необязательный интеграционный тест: он поднимает `postgres:17`
в Docker, применяет Up-секции миграций `00001`, `00010`, `00011`, создаёт
пользователя, пространство и одну официальную позицию, затем запускает
`migrate.py --apply` дважды и проверяет идемпотентность.

```bash
GRIST_TEST_INTEGRATION=1 .venv/bin/python -m pytest -m integration
```

Без `GRIST_TEST_INTEGRATION=1` тест пропускается.

## Ограничения

- Один `GET` на таблицу без постраничной загрузки: документ небольшой
  (208 материалов), но для больших документов API Grist нужно будет
  ограничивать/листать.
- Переносятся только перечисленные таблицы и колонки; вложения, картинки
  и история изменений не импортируются.
- Импорт ничего не удаляет: если строку убрали из Grist, она останется
  в базе.
- Если запуск с `--apply` нужно отменить, удаляйте данные осознанно:
  приватные позиции ищутся по `attrs->>'grist_id'` и
  `source = 'grist-import'`; глобальные позиции импорт не трогает.
