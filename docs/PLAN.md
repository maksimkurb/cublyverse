# Cublyverse — план

Cublyverse — персональный бот-ассистент: чат-бот в мессенджерах + WebApp + MCP.
Бот всегда работает от имени конкретного пользователя: вход по SSO (OIDC), а
аккаунты мессенджеров — это проверенные привязки к SSO-пользователю.

Первая фича — «Напоминания» (перенос n8n-воркфлоу «Cubly Reminder»). Дальше
фичи добавляются как отдельные модули.

Стори с критериями приёмки — в [STORIES.md](STORIES.md). Правила для
разработчиков и агентов — в [../AGENTS.md](../AGENTS.md). Оглавление
документации — в [README.md](README.md).

**Статус:** M0–M7 выполнены. Работает один бинарник с OpenAPI-конвейером,
PostgreSQL, входом SSO с безопасной привязкой мессенджеров, напоминаниями
(API, бот, планировщик, WebApp, MCP), персональными токенами, импортом из n8n
и документацией, которая проверяется в `make check`. Бэклог и известные
ограничения — в §7.

## 1. Принятые решения

| Тема | Решение | Почему |
|---|---|---|
| Язык бэкенда | Go 1.27.4 (см. `go.mod`), один модуль `github.com/maksimkurb/cublyverse` | unibot уже на Go |
| Бот-фреймворк | unibot перенесён в `unibot/` этого репозитория и дорабатывается на месте | это стартер, а не библиотека; правки нужны сразу |
| БД | PostgreSQL 17, `pgx/v5`, запросы через `sqlc`, миграции `goose` (встроены в бинарник) | требование; типобезопасный SQL без ORM |
| Файлы | S3-совместимый бакет, интерфейс `blob.Store` — только в бэклоге, сейчас не строим | пока файлов нет |
| API | spec-first: `api/openapi.yaml` (OpenAPI 3.0.3) — единственный источник правды | требование «OpenAPI + кодогенерация» |
| Кодген сервера | `oapi-codegen` → strict server на `net/http` + типы | стандарт для Go, без фреймворка |
| Кодген клиента | `openapi-typescript` + `openapi-fetch` + `openapi-react-query` | типы и клиент для WebApp |
| WebApp | React 18 + Vite + TypeScript + `@base-ui/react` и своя дизайн-система (`docs/WEBAPP.md`), сборка встраивается в бинарник (`embed`) | свой стиль и лёгкий бандл; сначала был `@telegram-apps/telegram-ui` |
| MCP | официальный `github.com/modelcontextprotocol/go-sdk`, Streamable HTTP на `/mcp` | требование |
| Идентичность | `users` в PG; `PrincipalID` = `users.id` (UUID); ключ пользователя — `(oidc_issuer, oidc_subject)` | SSO — источник истины |
| Сессии WebApp | непрозрачный токен, в БД хранится sha256; Bearer для Mini App, HttpOnly-cookie для браузера | без JWT, мгновенный отзыв |
| Доступ к MCP/API извне | персональные токены (PAT) `cv_pat_…`, создаются в WebApp | просто и привязано к пользователю; OAuth — в бэклоге |
| Планировщик | тикер в процессе + аренда строк в PG (`FOR UPDATE SKIP LOCKED` + `lock_until`) | догоняет пропуски, безопасен при нескольких репликах |
| Telegram | long polling (как в unibot), только личные чаты | webhook — в бэклоге |
| Логи | `log/slog`, JSON в проде | |
| Язык интерфейса | русский | как в n8n-версии |

## 2. Архитектура

```text
            Telegram            Matrix/Element          Браузер        MCP-клиент
               │                      │                    │               │
        unibot/platform/*      unibot/platform/*           │               │
               └──────────┬───────────┘                    │               │
                    unibot.Runtime                         │               │
                          │                                │               │
                   internal/bot (роутер)        internal/httpapi      internal/mcpserver
                          │                    (oapi-codegen strict)       │
                          └───────────────┬────────────────┴───────────────┘
                                          │
                       internal/features/<feature>/Service   ← вся бизнес-логика
                                          │
                              internal/store (sqlc, pgx)
                                          │
                                     PostgreSQL
```

Главное правило: **бот, HTTP API и MCP — три тонких входа в один и тот же
сервисный слой фичи**. Логика не дублируется, права проверяются в сервисе по
`PrincipalID`.

### Структура репозитория

```text
api/openapi.yaml              спецификация API (источник правды)
cmd/cublyverse/               main: serve | migrate | import-n8n | docs
internal/config/              конфигурация из env
internal/store/               pgxpool, миграции (goose), sqlc-запросы
internal/auth/                users, сессии, PAT, initData, middleware
internal/httpapi/             сгенерированный сервер + реализация strict-интерфейса
internal/mcpserver/           MCP-сервер, регистрация инструментов фич
internal/bot/                 роутер команд и действий, общие ответы
internal/features/reminders/  фича: сервис, расписание, планировщик, bot/mcp-адаптеры
internal/app/                 сборка всего вместе, Feature-реестр
unibot/                       фреймворк мессенджеров (перенесён, дорабатывается)
web/                          WebApp (Vite + React)
deploy/                       Dockerfile, docker-compose
docs/                         план, стори
```

### Модуль фичи

Каждая фича реализует интерфейс и регистрируется в `internal/app`:

```go
type Feature interface {
    Name() string
    RegisterBot(r *bot.Router)          // команды и префиксы действий
    RegisterMCP(s *mcp.Server)          // инструменты
    Jobs() []Job                        // фоновые задачи (планировщик)
}
```

HTTP-обработчики фичи встраиваются в общую реализацию strict-интерфейса
(один `openapi.yaml`, операции фичи помечены тегом). В WebApp фича — каталог
`web/src/features/<feature>` + запись в реестре маршрутов.

## 3. Идентичность и вход

1. Пользователь пишет боту. Привязки нет → бот шлёт кнопку «Войти».
2. Кнопка открывает `/auth/login?state=…` → OIDC (PKCE, nonce).
3. После возврата от OIDC показывается **страница подтверждения**: «Привязать
   Telegram-аккаунт X к SSO-аккаунту Y?». Привязка создаётся только после
   подтверждения (POST с одноразовым токеном).
4. Для Telegram дополнительно: страница входа открывается как Mini App, и
   сервер сверяет `initData.user.id` с ID из ожидающей привязки.

Пункты 3–4 закрывают атаку «подсунуть жертве свою ссылку входа»: без них
SSO-аккаунт жертвы привязался бы к мессенджеру атакующего.

WebApp:

- **Telegram Mini App**: `POST /api/v1/auth/telegram {init_data}` → сервер
  проверяет подпись (HMAC токеном бота), находит привязку → выдаёт сессию
  (Bearer). Привязки нет → `link_required` + ссылка на вход.
- **Браузер**: `/auth/login` без привязки мессенджера → OIDC → cookie-сессия.
- **Element-виджет**: OpenID-токен Matrix через Widget API → бэклог.

## 4. Напоминания: перенос логики n8n

Модель: `reminders` (правило) + `reminder_occurrences` (срабатывания, история).
У напоминания не больше одного активного срабатывания.

Поведение сохраняется один в один:

- расписание: дни недели (1–7, Пн=1) или дни месяца (1–31; несуществующий день
  = последний день месяца), время `HH:MM`, часовой пояс IANA;
- срабатывание по `next_due_at <= now`; пропущенные тики догоняются, после
  простоя отправляется одно срабатывание, следующее считается от «сейчас»;
- сообщение с кнопкой «✅ Выполнено»; пока не подтверждено — повтор каждые
  `repeat_minutes` (1–1440): новое сообщение, предыдущее удаляется, счётчик
  повторов растёт;
- подтверждение: сообщение заменяется на «✅ Выполнено: <время>», кнопка
  убирается; устаревшие/чужие/повторные нажатия получают понятный ответ;
- правка или выключение напоминания отменяет активное срабатывание и
  пересчитывает `next_due_at`;
- несколько времён в форме создают отдельные напоминания.

Что меняется осознанно:

- владелец — SSO-пользователь, а не Telegram user_id; доставка через
  `Runtime.SendToPrincipal` (Telegram, при ошибке — Matrix);
- подтверждение из любого мессенджера и через API/MCP;
- история срабатываний хранится (пригодится для статистики);
- аренда через `SKIP LOCKED` вместо lock-токенов.

Переезд: одноразовая команда `import-n8n` кладёт старые напоминания в таблицу
ожидания по Telegram user_id; они присваиваются пользователю при привязке
Telegram. Один токен бота — один поллер, поэтому при переключении n8n-воркфлоу
выключается.

## 6. Проверка плана на логичность

Что проверено и что из этого исправлено в плане:

1. **Привязка аккаунта была уязвима.** В unibot ссылка входа привязывает
   мессенджер к тому, кто по ней вошёл. Добавлены страница подтверждения и
   сверка `initData` (раздел 3, стори M1-4).
2. **Срок жизни кнопки.** В unibot токен действия живёт 24 часа в памяти, а
   повтор напоминания может быть раз в 1440 минут, и рестарт обнуляет память.
   Решение: хранилище действий в PG и TTL на действие (M1-2, M2-3).
3. **Ответ на нажатие.** n8n показывает «Подтверждено ✅» / «Это напоминание не
   для вас» во всплывашке; адаптер unibot отвечает на callback пустым ответом
   сразу. Нужен отложенный ответ с текстом (M2-2).
4. **Форматирование.** Текст напоминания использует `<b>`; `unibot.Message` —
   только plain text. Добавляется поле `HTML` (M2-1).
5. **Ошибки обработчика терялись.** `Runtime.consume` молча глотает ошибки —
   добавляется логирование (M2-4).
6. **Состояние OIDC в памяти.** Рестарт во время входа ломает вход — терпимо,
   но переносится в PG вместе с подтверждением привязки (M1-4).
7. **Один OpenAPI на всё.** MCP-инструменты OpenAPI не описываются — это другой
   протокол. Согласованность обеспечивается общим сервисным слоем; схемы
   инструментов выводятся из Go-структур SDK.
8. **Групповые чаты.** Привязка и напоминания только в личных чатах; адаптер
   Telegram игнорирует остальные (M2-5).
9. **Зависимости этапов.** M3 требует M2 (HTML, ответ на нажатие) и M1
   (пользователи); M4 требует сессий из M1 и API из M3; M5 требует сервисов M3.
   Циклов нет.

Открытые вопросы (не блокируют текущий выпуск):

- Какой бот будет боевым: текущий «Cubly Reminder Bot» (тогда нужен импорт и
  выключение n8n) или новый.
- Нужна ли Matrix-доставка напоминаний сразу или достаточно Telegram на старте
  (в плане: работает через общий механизм, отдельно не тестируется до бэклога).
- Нужен ли вход в MCP через OAuth (для коннектора claude.ai) или хватит PAT.

## 7. Бэклог (вне текущих этапов)

- Авторизация Element-виджета через Matrix OpenID.
- `blob.Store` + S3 (MinIO в compose) — когда появится фича с файлами.
- OAuth 2.1 resource server для MCP (RFC 9728) поверх OIDC-провайдера.
- Webhook-режим Telegram.
- Настройки пользователя: предпочитаемый мессенджер, часовой пояс по умолчанию.
- Обработка «бот заблокирован» (403): пометить привязку неактивной.
- Rate limiting на `/auth/*` и API.

### Известные ограничения текущей реализации

- **WebApp не проверялся визуально в настоящем клиенте Telegram** в рамках
  репозитория: сборка, API, типы и компонентные тесты зелёные, но вёрстку
  Mini App нужно один раз пройти руками на реальном устройстве.
- **Ограничение неудачных попыток PAT — в памяти процесса.** 20 попыток на
  remote IP с восстановлением по одной за 2 секунды; за reverse proxy это
  общий лимит на всех клиентов. Полноценный rate limiting — на прокси.
- **Присвоение старых напоминаний при привязке — best effort.** Сбой импорта
  не отменяет вход; строки остаются в `legacy_reminders_import` и подхватятся
  повторной привязкой или повторным `import-n8n`. Сообщение в чат об импорте
  тоже best effort.
- Matrix-доставка реализована общим механизмом, но в бою отдельно не
  тестировалась; Element-виджет и Matrix OpenID — в бэклоге.
