# Архитектура

Документ описывает, как устроен сервис: слои, потоки данных, модель
идентичности, бот-рантайм и планировщик. Он обновляется вместе с этапами
(`docs/PLAN.md`, `docs/STORIES.md`).

## 1. Слои

```text
       Telegram            Matrix/Element          Браузер        MCP-клиент
          │                      │                   │               │
   unibot/platform/*      unibot/platform/*          │               │
          └──────────┬───────────┘                   │               │
                unibot.Runtime                       │               │
                     │                               │               │
              internal/bot (Router)         internal/httpapi     internal/mcpserver
                     │                      (oapi-codegen strict)       │
                     └───────────────┬───────────────┴───────────────┘
                                     │
                     internal/features/<feature> (Service)  ← вся бизнес-логика
                                     │
                         internal/store (sqlc, pgx)
                                     │
                                PostgreSQL
```

Правила:

- **Бизнес-логика** живёт в `internal/features/<feature>`. Бот, HTTP API и MCP —
  тонкие адаптеры над одним и тем же сервисом; поведение не расходится между
  входами.
- **Контракты фичи** (`Feature`, `Job`) объявлены в `internal/feature` и
  реэкспортированы из `internal/app`. Отдельный пакет нужен, чтобы фича могла
  реализовать интерфейс без цикла импортов (`internal/app` сам собирает фичи).
- **Права** проверяет сервис по `PrincipalID`. Каждый запрос к данным ограничен
  владельцем; «дай всё, потом отфильтруем» не бывает.
- **`unibot/`** — транспортный фреймворк: типы сообщений, адаптеры мессенджеров,
  рантайм, реестр действий. Код фич не импортирует `unibot/platform/*`.
- `api/openapi.yaml` — источник правды для HTTP; сгенерированный код руками не
  правится. Схема БД — только через новые миграции `goose` и `sqlc`.

### Сборка в `internal/app`

`internal/app/app.go` — единственное место, где компоненты соединяются.
`app.New` делает следующее по порядку:

1. `store.Migrate` (goose) и `store.Open` (pgxpool) — схема приводится к
   текущей версии до открытия пула;
2. `auth.New` — пользователи, привязки, pending-входы, сессии и PAT;
3. `reminders.New` — сервис фичи с логгером и доставкой;
4. `reminders.NewFeature(service, ...)` → `NewRegistry(...)`;
5. `mcpserver.New(...)` → `registry.RegisterMCP(server)`;
6. `httpapi.New(httpapi.Deps{...})` — `Deps` получает тот же сервис напоминаний,
   `auth.Service` (и его `/auth/*`), WebApp, спецификацию и MCP-обработчик;
7. `startBot` — `bot.NewRouter`, `registry.RegisterBot(router)`, транспорты,
   `unibot.NewRuntimeWithConfig`, `delivery.attach(runtime)` и хуки
   `auth.OnLinked` / `auth.OnLegacyImported`;
8. `extraJobs` — `auth.cleanup` (сессии, `auth_pending`, отозванные PAT) и
   очистка просроченных `interactions`;
9. `App.Run` — `runtime.Start`, `jobs.Start(registry.Jobs() + extraJobs)`,
   `http.Server.ListenAndServe`, затем graceful shutdown: HTTP-сервер (10 с),
   отмена контекста, `runtime.Close`, ожидание задач, закрытие пула.

Сервис создаётся один раз. Бот, HTTP API и MCP получают один и тот же
`*reminders.Service`, поэтому поведение не может разойтись. Тестам доступны
`App.Handler()`, `App.Store()`, `App.Auth()`, `App.MCP()` и `App.Router()` —
поэтому сборку можно проверять без слушающего сокета.

## 2. Модель идентичности

`PrincipalID` — это `users.id` (UUID). Пользователь появляется только после
входа по OIDC; ключ пользователя — `(oidc_issuer, oidc_subject)`. Аккаунты
мессенджеров — проверенные привязки в `messenger_bindings`:

```text
OIDC-аккаунт (PrincipalID)
   ├── Telegram: remote_user_id, conversation_id
   └── Matrix:   MXID, room_id
```

Привязка создаётся только после подтверждения на отдельной странице (см.
`docs/API.md`). Перепривязка того же аккаунта мессенджера к другому
SSO-пользователю переносит строку, а не создаёт вторую.

Привязка Telegram ещё и забирает напоминания, импортированные из старого
n8n-бота: строки `legacy_reminders_import` с этим Telegram user id превращаются
в напоминания пользователя. Присвоение идёт после коммита привязки, одной
транзакцией на аккаунт: сбой импорта не отменяет вход (строки остаются ждать), а
`FOR UPDATE SKIP LOCKED` не даёт двум одновременным привязкам создать дубль.

Действие (кнопка) может быть дополнительно ограничено `PrincipalID`: это
переживает перепривязку мессенджера и не даёт «дожать» чужое напоминание.

## 3. Поток сообщения в боте

```text
Telegram/Matrix update
        │
        ▼
адаптер (unibot/platform/*)
  • только личные чаты (Telegram)
  • разбор команд /start, /help, /cmd@bot args
  • кнопки: непрозрачный токен → InteractionStore (PG)
        │  unibot.Event (+ AckToken для callback query)
        ▼
unibot.Runtime
  • Resolve identity: remote user → PrincipalID
  • проверка ограничения по PrincipalID
  • очередь на пользователя: события одного пользователя по порядку
  • таймаут, recover паник, логирование ошибок
        │  ResolvedEvent
        ▼
internal/bot.Router
  • /start, /help (ядро)
  • команды и префиксы действий фич (например, /reminders и reminders.*)
  • «не привязан» → кнопка «Войти»
  • ответ по умолчанию
        │
        ▼
internal/features/<feature> → сервис → PostgreSQL
```

### Роутер

`bot.Router` регистрируется один раз при старте (`Feature.RegisterBot`), поэтому
блокировок в горячем пути нет. Правила выбора обработчика:

1. Нет привязки → обработчик «не привязан» (по умолчанию — кнопка «Войти»).
2. Сообщение с командой → обработчик команды; неизвестная команда → подсказка
   `/help`.
3. Действие → обработчик самого длинного зарегистрированного префикса
   (`reminders.` или более точный `reminders.done`); без совпадения — «действие
   больше неактуально».
4. Всё остальное → ответ по умолчанию (для привязанного аккаунта — кнопка
   «Открыть приложение»).

Команды ядра — `/start` и `/help`; `/help` перечисляет всё, что
зарегистрировали фичи, и тот же список публикуется в меню Telegram
(`setMyCommands`). Команда фичи напоминаний — `/reminders`: короткий список
напоминаний пользователя и кнопка «Открыть приложение» (только для https
`PUBLIC_BASE_URL`, потому что `web_app`-кнопки требуют https).

Действия напоминаний регистрируются одним префиксом `reminders.`: обработчик
получает и `reminders.done`, и любое будущее действие фичи, поэтому добавление
нового действия не меняет роутер.

### HTML

`unibot.Message` содержит `Text` (plain-фолбэк) и необязательный `HTML` — строгое
подмножество `b`, `i`, `code`, `a href`. Telegram получает `parse_mode=HTML`,
Matrix — `format=org.matrix.custom.html` и `formatted_body`; `Text` остаётся
`body`. Валидатор (`unibot.ValidateHTML`) отвергает любые другие теги и
атрибуты, поэтому разметка из пользовательских данных всегда проходит через
`unibot.EscapeHTML`.

### Ответ на нажатие (Ack)

Кнопка Telegram должна получить `answerCallbackQuery`, иначе у клиента крутится
индикатор. Раньше адаптер отвечал сразу и пусто, и всплывающее сообщение было
невозможно.

Теперь:

- адаптер не отвечает сам: id callback query едет в `Event.AckToken`;
- обработчик вызывает `botctx.Ack(ctx, text, alert)` — текст показывается
  всплывашкой, `alert=true` делает её модальной;
- если обработчик не ответил, рантайм после его завершения отправляет пустой
  ответ (в том числе после таймаута и паники);
- для событий без `AckToken` (Matrix) `Ack` — no-op.

События, для которых обработчик не запускается (чужой или просроченный токен,
не-private чат), адаптер подтверждает сам — индикатор не должен зависать.

### Действия: TTL и payload

`unibot.Action`:

| Поле | Смысл |
|---|---|
| `ID` | смысл действия (`reminders.done`); по префиксу его находит роутер |
| `Payload` | непрозрачная строка до 512 байт, возвращается в `ActionEvent` |
| `PrincipalID` | необязательное ограничение на SSO-аккаунт |
| `TTL` | срок жизни кнопки, по умолчанию 24 часа (`DefaultActionTTL`) |

Payload существует потому, что Telegram ограничивает `callback_data` 64
байтами: идентификаторы (напоминание + срабатывание) живут в
`interactions.payload` и приходят обработчику в `ActionEvent.Payload`.

TTL попадает в `interactions.expires_at`; просроченная кнопка не разрешается
(запрос фильтрует по `now()`), поэтому её нельзя «дожать» после рестарта или
спустя сутки.

## 4. Гарантии рантайма

- **Порядок.** События одного remote user обрабатываются строго по одному и в
  порядке поступления. Разные пользователи обрабатываются параллельно.
- **Ограниченность.** Не больше `MaxConcurrentHandlers` (по умолчанию 32)
  одновременных обработчиков, не больше `MaxPendingEvents` (1024) ожидающих
  событий и ограниченный канал между транспортом и планировщиком. Переполнение
  создаёт давление на транспорт, а не бесконечные горутины.
- **Изоляция ошибок.** Ошибка обработчика и ошибка `Resolve` логируются через
  `log/slog`; паника обработчика перехватывается и не роняет процесс.
- **Таймаут.** Обработчик получает контекст с таймаутом
  (`BOT_HANDLER_TIMEOUT`, по умолчанию 30 секунд); по истечении работа
  прерывается, в лог пишется `bot handler timed out`.
- **Остановка.** `Runtime.Close` отменяет контекст, закрывает транспорты,
  дожидается планировщика и обработчиков (с ограничением по времени) и
  идемпотентен.

## 5. Транспорты

- **Telegram** — long polling. Обслуживаются только личные чаты: сообщения и
  callback-запросы из групп, супергрупп и каналов игнорируются. При старте
  публикуются команды (`setMyCommands`, scope `all_private_chats`, язык `ru`) и
  кнопка меню Mini App (`setChatMenuButton`) — если задан https
  `PUBLIC_BASE_URL`. Ошибки этих вызовов логируются и не мешают работе бота.
- **Matrix** — `mautrix-go` с E2EE. Действия рендерятся «засеянными» реакциями,
  выборы — опросами (MSC3381). Подтверждение нажатия не требуется.

## 6. HTTP API и MCP

HTTP-слой генерируется из `api/openapi.yaml` (strict server): обработчики —
тонкие адаптеры над сервисами фич, ошибки отдаются единым JSON. Подробности
HTTP — `docs/API.md`.

Фото позиций WebApp получает через `internal/imageproxy`
(`GET /api/v1/images`, подписанные ссылки, только публичные адреса; см.
[`API.md`](API.md)).

MCP живёт на `/mcp` (`internal/mcpserver`) и использует официальный
`github.com/modelcontextprotocol/go-sdk`:

```text
MCP-клиент ──POST /mcp (Streamable HTTP)──► mcpserver.Handler
                                                │  Authorization: Bearer cv_pat_…
                                                ▼
                                        auth.ResolveAPIToken → Principal{id, scopes}
                                                │  context
                                                ▼
                                        feature.RegisterMCP → tool handler
                                                │
                                                ▼
                                        reminders.Service (тот же, что у бота и API)
```

- **Stateless.** Каждый JSON-RPC запрос — отдельный HTTP-запрос; сервер не
  хранит сессии, не поддерживает standalone SSE (`GET /mcp` → `405`) и не
  требует sticky sessions. Рестарт или другая реплика не рвут клиента, а
  инструментам состояния между вызовами не нужно.
- **Только PAT.** Cookie-сессия на `/mcp` не принимается: MCP-клиент — не
  браузер, а PAT явный, отзываемый и ограниченный областями доступа. Так на
  машинном эндпоинте нет ambient credential.
- **Principal в контексте.** Middleware резолвит токен и кладёт `Principal{ID,
  Scopes}` в `context`; каждый инструмент проверяет свой scope и вызывает
  сервис фичи. Токен не может управлять токенами или менять профиль — эти
  операции сессионные.
- **Регистрация.** `feature.Feature.RegisterMCP(*mcpserver.Server)` — та же
  схема, что `RegisterBot`: фича приносит свои инструменты, ядро регистрирует
  `whoami`. Схемы инструментов выводятся из Go-структур с `jsonschema`-тегами,
  а `docs/MCP.md` генерируется из живого сервера и проверяется в `make check`.

Подробности, все инструменты, схемы и подключение клиентов — `docs/MCP.md`.

## 7. WebApp

WebApp — отдельный фронтенд-слой (`web/`), который не содержит бизнес-логики:
он вызывает тот же HTTP API, что бот и MCP. Сборка Vite встраивается в
Go-бинарник и отдаётся по `/app/`; `/` редиректит туда же.

```text
Telegram Mini App        Браузер / Matrix-виджет
        │                          │
        ▼                          ▼
   web/src/host  ← мост: тема, haptics, диалоги, «назад», ссылки, close
        │
        ▼
   web/src/auth  ← Bearer в памяти (Telegram) или HttpOnly cookie (браузер)
        │
        ▼
   openapi-fetch + openapi-react-query  ← типы из api/openapi.yaml
        │
        ▼
   /api/v1/*  →  internal/httpapi  →  сервисы фич
```

- **Мост к хосту.** Компоненты не знают про `Telegram.WebApp`: они работают с
  `HostBridge` (`telegram` | `matrix` | `browser`). Telegram-ветка берёт тему,
  haptics и нативные диалоги из Mini App SDK; браузер — из `matchMedia` и
  `window`. Matrix распознаётся, но пока ведёт себя как браузер.
- **Вход.** Mini App меняет `initData` на Bearer-сессию; токен хранится только в
  памяти. Браузерная сессия — `HttpOnly` cookie. Общий middleware ставит
  `Authorization`, добавляет `Content-Type` изменяющим запросам с cookie и один
  раз повторяет запрос после `401`, переавторизовавшись.
- **Маршруты** — history под базой `/app/` (`/app/reminders`): сервер отдаёт
  `index.html` на любой такой путь, а фрагмент с Telegram `initData` не
  затрагивается.
- **Фичи** подключаются каталогом `web/src/features/<feature>` и одной строкой в
  реестре; главный экран и роутер собираются из реестра.
- Подробности, схема входа и рецепт новой фичи — [WEBAPP.md](WEBAPP.md).

## 8. Фоновые задачи

`internal/app.Runner` запускает по горутине на задачу и ждёт их остановки.
Задачи фич (например, планировщик напоминаний) и служебные (очистка сессий,
`auth_pending`, просроченных `interactions`) получают общий контекст и
завершаются по нему. Паника в задаче логируется и не останавливает остальные.

### Планировщик напоминаний

```text
тик (15 с, REMINDERS_TICK_INTERVAL)
   │
   ├─ короткая транзакция: ClaimDueReminders (FOR UPDATE SKIP LOCKED, lease 55 с)
   │
   ├─ отправка вне транзакции: Delivery (Telegram → Matrix через Runtime)
   │
   └─ вторая транзакция: запись срабатывания и next_due_at под той же арендой
```

- **Аренда вместо блокировки на всё время отправки.** Строка резервируется на
  55 секунд (`lock_until`), транзакция сразу закрывается, и только потом идёт
  сетевой вызов. Медленный мессенджер не держит блокировки базы.
- **Несколько реплик.** `FOR UPDATE SKIP LOCKED` не даёт двум экземплярам взять
  одну строку, а вторая транзакция проверяет аренду из момента захвата:
  первое срабатывание — `lock_until` и `updated_at` (чтобы не перезаписать
  правило, изменённое пользователем), повтор — `lock_until`. Опоздавший
  рабочий получает `ErrLeaseLost` и ничего не перезаписывает.
- **Догон.** После простоя отправляется одно срабатывание, а `next_due_at`
  считается от текущего момента.
- **Ошибки доставки** попадают в `reminders.last_error`, аренда снимается, и
  следующий тик повторяет отправку: сбой мессенджера откладывает напоминание, а
  не теряет его.

### Абстракция доставки

Фича не импортирует `unibot/platform/*`. Она объявляет интерфейс
`reminders.Delivery` (`Send`, `Edit`, `Delete`), а реализация в `internal/app`
переводит его в вызовы `unibot.Runtime`:

```text
reminders.Scheduler ──► reminders.Delivery ──► unibot.Runtime ──► transport
        │                                             │
        └── deliveries jsonb (platform, chat, message)┘
```

`Send` идёт через `SendToPrincipal` с предпочтением Telegram → Matrix: сообщение
получает первый успешный транспорт. Ссылки на отправленное сохраняются в
`reminder_occurrences.deliveries`, поэтому повтор удаляет предыдущее сообщение
(`Delete`), а подтверждение — из бота или из WebApp — заменяет текущее (`Edit`).
Без настроенных транспортов `Send` возвращает ошибку, и планировщик пишет её в
`last_error`: сервис с одной базой остаётся работоспособным.
